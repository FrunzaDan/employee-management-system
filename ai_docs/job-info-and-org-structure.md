# Job info & org structure (offices/departments/cost centers/salary history)

## What it is

A "Job information" card on the employee details/add/edit pages (hire date, office, department, cost center, current brutto salary), backed by three new fully-CRUD-able org lookup tables and an append-only salary history table, both linked to `tbl_employees` by GUID.

## How it works

- **Offices/departments/cost centers** are plain GUID-keyed lookup tables (server-generated GUIDs, same convention as everywhere else in this app), each with a full CRUD stored-proc set following the `(result, message)` / `ISNULL`-partial-update conventions from `usp_createEmployee`/`usp_editEmployee`. Their list procs (`usp_get{Offices,Departments,CostCenters}`) are **unpaginated** — small reference data, not a growing operational table like `tbl_employees`.
- **Each list proc also aggregates `employee_count`/`total_brutto_salary`** (`OfficeModel`/`DepartmentModel`/`CostCenterModel`'s `EmployeeCount`/`TotalBruttoSalary`, shown as "Employees"/"Total brutto salary" columns on the `/offices`, `/departments`, `/costCenters` admin tables) — a `LEFT JOIN` to `tbl_employees` + the same `OUTER APPLY ... ORDER BY effective_Date DESC` "current salary" pattern `usp_getEmployees` uses, `GROUP BY`'d and summed. Counts/sums every assigned employee regardless of status (active/deactivated/test), same scope as `usp_getEmployeesByOffice`/`ByDepartment`/`ByCostCenter`. The single-entity `usp_get{Office,Department,CostCenter}` (used by the details pages) does **not** compute these — `DbHelper` has a separate `Map*ListItemFromReader` for the list shape rather than making the columns optional on the shared row mapper.
- **`tbl_employees`** gets three nullable FK columns (`FK_office_guid`/`FK_department_guid`/`FK_cost_center_guid`) plus `hire_Date` (`DATE`, same as `birthdate`). All org PKs/FKs are `UNIQUEIDENTIFIER`, and each FK column has a covering index (see [database](database.md)). `usp_createEmployee`/`usp_editEmployee` pre-check each guid exists before touching the FK (`400` "Office/Department/Cost center not found") — same pattern as the email/msisdn duplicate pre-checks — so an unknown guid never surfaces as a raw FK-violation `500`.
- **Deleting an office/department/cost-center that's still assigned to an employee is blocked**: each `usp_delete*` pre-checks `tbl_employees` for that FK and returns `409` instead of letting the (intentionally `NO ACTION`, no cascade) FK constraint throw.
- **Salary is append-only history**, not a field: `tbl_employee_salary_history` (`PK_salary_guid`, `FK_employee_guid`, `brutto_salary`, `effective_Date`, `created_Date`) has one row per change. There is **no edit/delete** for a salary entry — a correction is just a new entry with a later effective date, mirroring how real payroll changes are recorded. `usp_getEmployee`/`usp_getEmployees` surface only the *current* value via `OUTER APPLY (SELECT TOP 1 ... ORDER BY effective_Date DESC)`, backed by `IX_tbl_employee_salary_history_employee_effective (FK_employee_guid, effective_Date DESC)`. The full history is fetched separately via `GET /api/Employee/salaryHistory?employeeGuid=`.
- **Initial salary is deliberately not part of employee creation** — `usp_createEmployee` has no salary parameter at all. A new employee gets its first salary the same way a raise later does: a call to `usp_addEmployeeSalary` (`POST /api/Employee/salaryHistory`), made from the employee-details page's "Salary history" card right after creation. This keeps create/edit's shape unchanged and avoids a create-only side-effect.
- **`usp_deleteEmployee`** now also deletes the employee's `tbl_employee_salary_history` rows (no cascade FK, same reasoning as `tbl_addresses`) in the same transaction, before the employee row.
- **Angular job-info form fields** (`hireDate`, `officeGuid`, `departmentGuid`, `costCenterGuid`) are required in `employeeFormSchema`, same as every other field on that form ("All fields are required" note) — office/department/cost-center are populated into `<select>`s from `OfficeService`/`DepartmentService`/`CostCenterService`, loaded once per form instance in `EmployeeFormFieldsComponent.ngOnInit`.
- **Admin CRUD pages** (`/offices`, `/departments`, `/costCenters`) are each a single component: a table + one inline form reused for both add and edit (toggled by a `draft` signal), not a separate add/edit route pair like employees — these entities are 1–3 fields with no status lifecycle, so a page split would be excessive. Mutations reload the whole list afterward (`OfficeService.loadOffices()` etc.) rather than patching it locally, since the lists are always small.
- **Two ways to see an office/department/cost center's employees, at different depths**:
  - The **"Quickly view employees" button** expands the row in place with a compact name/email/status list — fetched on demand from `usp_getEmployeesByOffice`/`ByDepartment`/`ByCostCenter` via a `GET .../employees?guid=` endpoint on each controller, not loaded eagerly for every row. At most one row per page is expanded at a time (`expandedOfficeGuid`/`expandedDepartmentGuid`/`expandedCostCenterGuid`), and the result is discarded (not cached) when collapsed or when a different row is expanded.
  - **Clicking the entity's name/code itself** navigates to its dedicated details page (`OfficeDetailsComponent` etc.) — same `?id=` query-param binding as `EmployeeDetailsComponent.id` (via `withComponentInputBinding()`), showing the entity's own fields plus the *same* employees list in full-table form (also via `getEmployees(guid)`), each row linking to `/employeeDetails`.
  - Both reuse the three services' `getEmployees(guid)` method, which returns a plain `Observable<EmployeeSummary[]>` rather than updating signal state — a one-off read for a page-local concern, not shared list state (like `fetchOfficesOnce` etc). The details pages additionally use a new single-entity `getOffice`/`getDepartment`/`getCostCenter(guid)` method, hitting the same `GET get?guid=` endpoint the admin pages' edit form doesn't use today (it edits from the already-loaded list).

- **The About page's "add 50 test employees" bulk generator** (`about.component.ts`) also generates job info: a random hire date between 2018 and 2025 (`randomHireDate`), a random office/department/cost center picked from `OfficeService.fetchOfficesOnce`/`DepartmentService.fetchDepartmentsOnce`/`CostCenterService.fetchCostCentersOnce` (one-off `Observable`-returning reads, distinct from those services' signal-backed `loadX()` used by the admin CRUD pages), and a random initial brutto salary added via `SalaryHistoryService.addSalarySilently` after the employee is created (its guid isn't returned by registration, so it's looked up via `GetEmployeeService.findEmployeeGuid(email)` first, same technique the generator already used before this feature existed). A failed guid lookup or salary add is swallowed, same "already succeeded, don't fail it retroactively" reasoning as `EmployeeAuditLogger` — it doesn't count against the added/failed tally shown in the summary toast.

## Gotchas / conventions

- Office/department/cost-center CRUD is **not** audit-logged — that's an employee-specific feature (`tbl_employee_audit_log`); adding a raise **is** audit-logged (`EmployeeAuditLogger`, action `"Salary changed"`), same as every other employee mutation.
- `EmployeeFormFieldsComponent` now depends on `OfficeService`/`DepartmentService`/`CostCenterService` (real `HttpClient`-backed services) — any test that renders it via `fixture.detectChanges()` (e.g. `edit-employee.component.spec.ts`) must stub these three in `TestBed`, same as it already stubs `GetEmployeeService`, or the fixture throws for lack of a provided `HttpClient`. `employee-details.component.spec.ts` needs the same treatment for `SalaryHistoryService`.
- `Employee.hireDate`/`officeGuid`/`departmentGuid`/`costCenterGuid`/`officeName`/`departmentName`/`costCenterName`/`currentBruttoSalary` are all **optional** on the Angular `Employee` interface (unlike the required job-info *form* fields) — existing employees created before this feature have none of this set, and `birthdate`-style "always a string" typing would be misleading for genuinely-absent data.

## Known gaps / deliberately deferred

- No pagination on the org lookup lists or per-employee salary history — same reasoning as `usp_getEmployeeAuditLog`: bounded, small-in-practice datasets.
- No bulk assignment (e.g. "move all employees from office A to office B") — out of scope for this pass; reassigning an employee's office/department/cost-center happens one employee at a time via the normal edit form.
