# Job info & org structure (offices/departments/cost centers/salary history)

## What it is

A "Job information" card on the employee details/add/edit pages (hire date, office, department, cost center, current gross salary), backed by three new fully-CRUD-able org lookup tables and an append-only salary history table, both linked to `Employee` by GUID.

## How it works

- **Offices/departments/cost centers** are plain GUID-keyed lookup tables (DB-generated `NEWSEQUENTIALID()` keys, same convention as everywhere else in this app), each with a full CRUD stored-proc set following the `(Result, Message)` / `ISNULL`-partial-update conventions from `Employee_Create`/`Employee_Update`. Their list procs (`{Office,Department,CostCenter}_List`) are **unpaginated** — small reference data, not a growing operational table like `Employee`.
- **Each list proc also aggregates `EmployeeCount`/`TotalGrossSalary`** (`OfficeModel`/`DepartmentModel`/`CostCenterModel`'s `EmployeeCount`/`TotalGrossSalary`, shown as "Employees"/"Total gross salary" columns on the `/offices`, `/departments`, `/cost-centers` admin tables) — a `LEFT JOIN` to `Employee` + the same `OUTER APPLY ... ORDER BY EffectiveDate DESC` "current salary" pattern `Employee_List` uses, `GROUP BY`'d and summed. Counts/sums every assigned employee regardless of status (active/deactivated/test), same scope as `Employee_ListByOffice`/`ByDepartment`/`ByCostCenter`. The single-entity `{Office,Department,CostCenter}_Get` (used by the details pages) does **not** compute these — `DbHelper` has a separate `Map*ListItemFromReader` for the list shape rather than making the columns optional on the shared row mapper.
- **`Employee`** gets three nullable FK columns (`OfficeId`/`DepartmentId`/`CostCenterId`) plus `HireDate` (`DATE`, same as `BirthDate`). All org PKs/FKs are `UNIQUEIDENTIFIER`, and each FK column has a covering index (see [database](database.md)). `Employee_Create`/`Employee_Update` pre-check each ID exists before touching the FK (`400` "Office/Department/Cost center not found") — same pattern as the Email/PhoneNumber duplicate pre-checks — so an unknown guid never surfaces as a raw FK-violation `500`.
- **Deleting an office/department/cost-center that's still assigned to an employee is blocked**: each `<Entity>_Delete` pre-checks `Employee` for that FK and returns `409` instead of letting the (intentionally `NO ACTION`, no cascade) FK constraint throw.
- **Salary is append-only history**, not a field: `EmployeeSalary` (`EmployeeSalaryId`, `EmployeeId`, `GrossSalary`, `EffectiveDate`, `CreatedAt`) has one row per change. There is **no edit/delete** for a salary entry — a correction is just a new entry with a later effective date, mirroring how real payroll changes are recorded. `Employee_Get`/`Employee_List` surface only the *current* value via `OUTER APPLY (SELECT TOP 1 ... ORDER BY EffectiveDate DESC)`, backed by `IX_EmployeeSalary_EmployeeId_EffectiveDate_CreatedAt (EmployeeId, EffectiveDate DESC)`. The full history is fetched separately via `GET /api/employee/salary-history?employeeId=`.
- **Initial salary is deliberately not part of employee creation** — `Employee_Create` has no salary parameter at all. A new employee gets its first salary the same way a raise later does: a call to `EmployeeSalary_Create` (`POST /api/employee/salary-history`), made from the employee-details page's "Salary history" card right after creation. This keeps create/edit's shape unchanged and avoids a create-only side-effect.
- **`Employee_Delete`** now also deletes the employee's `EmployeeSalary` rows (no cascade FK, same reasoning as `EmployeeAddress`) in the same transaction, before the employee row.
- **Angular job-info form fields** (`hireDate`, `officeId`, `departmentId`, `costCenterId`) are required in `employeeFormSchema`, same as every other field on that form ("All fields are required" note) — office/department/cost-center are populated into `<select>`s from `OfficeService`/`DepartmentService`/`CostCenterService`, loaded once per form instance in `EmployeeFormFieldsComponent.ngOnInit`.
- **Admin CRUD pages** (`/offices`, `/departments`, `/cost-centers`) are each a single component: a table + one inline form reused for both add and edit (toggled by a `draft` signal), not a separate add/edit route pair like employees — these entities are 1–3 fields with no status lifecycle, so a page split would be excessive. Each list is an `httpResource` in its service (nothing fetched until the first `loadX()`, `reload()` after that; errors through `extractErrorMessage`, like the customer app's `ProductService`), and mutations reload the whole list afterward (`OfficeService.loadOffices()` etc.) rather than patching it locally, since the lists are always small. The office/department/cost-center details pages read the entity and its employees through two `rxResource`s keyed on the route's id input (like Imalo's `ScholarDetailsComponent`). `office.service.spec.ts` pins the shared service shape; `salary-history.service.spec.ts` the per-employee history.
- **Two ways to see an office/department/cost center's employees, at different depths**:
  - The **"Quickly view employees" button** expands the row in place with a compact name/email/status list — fetched on demand from `Employee_ListByOffice`/`ByDepartment`/`ByCostCenter` via a `GET .../employees?<entity>Id=` endpoint on each controller, not loaded eagerly for every row. At most one row per page is expanded at a time (`expandedOfficeGuid`/`expandedDepartmentGuid`/`expandedCostCenterGuid`), and the result is discarded (not cached) when collapsed or when a different row is expanded.
  - **Clicking the entity's name/code itself** navigates to its dedicated details page (`OfficeDetailsComponent` etc.) — same route-param binding as `EmployeeDetailsComponent.employeeId` (via `withComponentInputBinding()`), showing the entity's own fields plus the *same* employees list in full-table form (also via `getEmployees(guid)`), each row linking to `/employees/:employeeId`.
  - Both reuse the three services' `getEmployees(id)` method, which returns a plain `Observable<EmployeeSummary[]>` rather than updating signal state — a one-off read for a page-local concern, not shared list state (like `fetchOffices` etc). The details pages additionally use a new single-entity `getOffice`/`getDepartment`/`getCostCenter(guid)` method, hitting the same `GET get?guid=` endpoint the admin pages' edit form doesn't use today (it edits from the already-loaded list).

- **The About page's "add 50 test employees" bulk generator** (`about.component.ts`) also generates job info: a random hire date between 2018 and 2025 (`randomHireDate`), a random office/department/cost center picked from `OfficeService.fetchOffices`/`DepartmentService.fetchDepartments`/`CostCenterService.fetchCostCenters` (one-off `Observable`-returning reads, distinct from those services' `httpResource`-backed `loadX()` used by the admin CRUD pages), and a random initial gross salary added via `SalaryHistoryService.createSalarySilently` after the employee is created, using the `employeeId` registration returns as its `data`. A failed salary add is swallowed, same "already succeeded, don't fail it retroactively" reasoning as `EmployeeAuditLogger` — it doesn't count against the added/failed tally shown in the summary toast.

## Gotchas / conventions

- Office/department/cost-center CRUD is **not** audit-logged — that's an employee-specific feature (`EmployeeAuditLog`); adding a raise **is** audit-logged (`EmployeeAuditLogger`, action `SalaryChanged`, shown in the UI as "Salary changed"), same as every other employee mutation.
- `EmployeeFormFieldsComponent` now depends on `OfficeService`/`DepartmentService`/`CostCenterService` (real `HttpClient`-backed services) — any test that renders it via `fixture.detectChanges()` (e.g. `update-employee.component.spec.ts`) must stub these three in `TestBed`, same as it already stubs `EmployeeService`, or the fixture throws for lack of a provided `HttpClient`. `employee-details.component.spec.ts` needs the same treatment for `SalaryHistoryService`.
- `Employee.hireDate`/`officeId`/`departmentId`/`costCenterId`/`officeName`/`departmentName`/`costCenterName`/`currentGrossSalary` are all **optional** on the Angular `Employee` interface (unlike the required job-info *form* fields) — existing employees created before this feature have none of this set, and `birthDate`-style "always a string" typing would be misleading for genuinely-absent data.

## Known gaps / deliberately deferred

- No pagination on the org lookup lists or per-employee salary history — same reasoning as `EmployeeAuditLog_ListByEmployee`: bounded, small-in-practice datasets.
- No bulk assignment (e.g. "move all employees from office A to office B") — out of scope for this pass; reassigning an employee's office/department/cost-center happens one employee at a time via the normal edit form.
